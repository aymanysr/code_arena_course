CAMPUS PUZZLE RACE / SPEC NOTES

Prototype ready for Team review — 2026-09-18

Two teams. One locked campus. Three puzzles stand between you and the reboot.

A competitive web game for the 42 ft_transcendence project, built in one month. Two teams cooperate internally to solve a C-fundamentals escape room and restore a fictional campus computer system before the other team.

01

The game

One campus-lockdown room, three sequential stages, two isolated teams racing the same puzzle instance.

Stage 1

Loop tracing

Follow loops and conditions to a value. Later clues open only after a pass.

Stage 2

String reasoning

Index and compare characters. Progress, clues and chat stay isolated per team.

Stage 3

Array-function repair

Assemble the fixed function output. Templates avoid undefined or platform-dependent C; seeds repeat instances for checking but stay hidden in play.

Roles

One balanced role per player

Each stage splits clues and controls so every role is essential. 2-player and 3-player layouts differ — nobody ever holds two roles, and no puzzle needs three simultaneous physical actions.

Fairness core. Both teams get the same size and the same puzzle instance. Example split — one player holds the code and picks a transformation, the other holds the inputs and assembles the output. In 3-player mode that work divides into three essential parts.

Timing and penalties

The clock never pauses for penalties. Cooldowns price wrong answers; hint delays price help — the two stack independently.

Cooldown

During the wait

  • Read, discuss, change the proposal — but no resubmit
  • No attempt limit; bad transport or duplicate requests never count as wrong
Hints

Priced help

  • Two hints per stage, progressively more useful, bought once per team
  • One teammate asks, a different teammate confirms; cost shown first
  • Hints guide only — never the full solution
Idempotency

Safe retries

  • Every submit carries a request id; retries replay the outcome, never a second penalty
  • A new submit mid-cooldown is rejected without another failure count
Disconnects

Seat kept

  • Seat and role reserved to match end; private clues never transfer
  • Timer and cooldowns continue; reconnect re-auths and restores snapshot
  • Unrecoverable restart: unfinished matches marked interrupted, no win or loss
04

Seven defaults up for review

Game, stack, boundaries, scoring target, retries, hints, reconnection and schedule are already approved in conversation. These seven complete the design and need sign-off with this document.

D1

Private lobbies, no matchmaking yet

Invitation-code lobbies only. Host picks 2v2 or 3v3; every player must be ready before start.

D2

Two hints per stage, dual control

Each bought once per team. Any teammate may ask; a different teammate must confirm.

D3

Anyone submits, server serializes

Any teammate may submit the assembled answer. Stages need valid input through each role's controls; concurrent actions serialize per team.

D4

Server times decide, ties draw

Completion eligibility times come from the server. Exact tie is a draw; a time at or past the deadline never wins.

D5

Explicit 42 account linking

Link 42 while signed in with email/password; later 42 logins follow the link. Matching emails alone never link; unlinked 42 logins are sent to register/sign in and link.

D6

One instance per service

Redis holds expiring presence/session-revocation data; PostgreSQL owns durable business data. Live recovery of an active match after a game restart stays out of scope.

D7

Chat ownership: Amal

Amal owns the chat backend plus chat integration, Saad reviews auth and service boundaries. The supporting developer takes bounded tasks reviewed by the relevant lead.

07

Auth, storage and failure handling

Trust nothing from the browser; persist before acknowledging; degrade loudly, never silently.

Tokens

Signed, verified locally

  • Core hashes and salts passwords, signs tokens, keeps the secret
  • Game and chat verify signatures locally and authorize every action
  • Expiry, refresh rotation, logout and revocation cover HTTP and WebSocket alike
Sessions

Cookies and OAuth

  • Secure HttpOnly cookies, same-site, origin checks, cross-site-change protection
  • OAuth verifies callback state; outage leaves password login working
Avatars

Validated files

  • Size and content validated; server-generated safe filenames
  • Persistent volume; Nginx serves files read-only; default avatar until success
  • Users replace only their own; rejected uploads keep the old image
Authority

Game decides

  • Old or manipulated client values never win; role/team/match checks on everything
  • PostgreSQL writes and dedup finish before any durable success is reported
  • Redis is never the source of truth for scores or answers
Chat down? Show the connection state and retry — never mark messages delivered until acknowledged. Game state and the match clock carry on regardless.

09

Verification — eight acceptance checks

Every check must pass before the team calls the release done. Timing tests inject a clock instead of waiting in real time.

V1

Puzzle checks

Every template × team size is solvable, each role matters, clues match the solution, C semantics stay safe. Exhaust small domains; sample fixed seeds for large ones.

V2

State checks

Wrong answers, cooldown ladder and reset, hint confirm/dedup, finish delays, ties and the deadline edge all produce the defined outcome.

V3

Concurrency checks

Simultaneous requests can never duplicate a role, double-advance a stage, double-apply a hint, double-count a retry, or finalize twice.

V4

Access checks

Another role's data, opponents' messages, private endpoints and other players' avatars stay unreachable — including via direct requests and forged sockets.

V5

Multiplayer checks

Full 2v2 and 3v3 matches, concurrent matches, realistic delay, refresh, disconnect, expired auth and reconnection with correct filtered state.

V6

Failure checks

Restart game mid-match and after a finished match: interruption without a fabricated loss, completed result preserved, chat and dependencies degrade usably.

V7

Delivery checks

One-command clean start, data survives container recreation, HTTPS/WSS, clean console, responsive and keyboard-usable UI, both policy pages, every module demo.

V8

Defense rehearsal

All contributors explain their work and the design; rehearse one small live change for the PDF's possible evaluation request.

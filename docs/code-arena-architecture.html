FT_TRANSCENDANCE · CODE ARENA · SYSTEM DESIGN BRIEF

A fair coding battle needs one authority.

The browser is the workstation. The Game service is the referee. The judge runs untrusted code in isolation. This page maps the boundary between those responsibilities — and labels what is proven today versus what still needs team sign-off.

04 / Critical path

What happens in one match

The browser asks. The Game service validates and persists. The judge executes. The Game service reveals.

01 · ENTRY

Lobby → match

Private room or queue creates a 1v1/2v2 match. Membership and sides are server-owned.

02 · CODING

Round is opened

Game sends a filtered snapshot: problem, starter, visible tests, own/team document, and readiness.

03 · RUN

Visible feedback

Run evaluates visible examples only. It never receives or returns hidden-suite material.

04 · SUBMIT

Hidden evaluation

Submit seals an attempt, sends code to the isolated judge, and keeps scores hidden until reveal.

05 · SCORE

Game commits verdict

Game calculates weighted 0–100 round score, stores the counted result, and deduplicates retries by request ID.

06 · REVEAL

Round becomes visible

When the reveal condition is met, the Game service publishes the per-group result and cumulative score.

07 · ROTATE

New problem

Three rounds by default. Code, visible tests, readiness, and document revision reset; match score carries forward.

08 · RESULT

Persist once

Final total uses round-score sums, then scoring time, then submission count, then draw.

2v2 extension: the team shares one Yjs document per round. Both teammates must be Ready against the current document revision before Submit is allowed. Collaboration traffic changes the document; it never changes the authoritative phase, score, or reveal rules.
05 / Realtime transport

Four channels, four kinds of traffic

Separating channels prevents a cursor update, chat message, or socket loss from accidentally becoming a game transition.

/ Game authority

Phase, Run, Submit, readiness, clock, presence, reveal, result. The Game gateway re-resolves the caller’s identity and membership before acting.

/lobby Entry flow

Queue and private rooms. Matchmaking is serialized with Postgres locks; room updates and match-found events go to the relevant members.

/collab 2v2 Yjs

Shared text and awareness only. Authorization happens before sync; accepted updates persist to the team document and bump the application revision.

/chat 2v2 social

Team messages and quick pings. Game owns the namespace and enforces team-room isolation/rate limits; durable Game-owned history remains next.

06 / Trust boundaries

Data ownership and security invariants

These are the rules teammates should use when reviewing endpoints, events, and persistence changes.

Game DB

Matches, submissions, reveals

  • Authoritative phase and participant state
  • Request identifiers for idempotent retries
  • Collab rows and durable reveal records
Core DB

Identity and account state

  • Password hashes and refresh sessions
  • OAuth links and profile metadata
  • Friends and avatar records
Hidden data

Never cross the browser boundary

  • Hidden tests and opponent source
  • Unrevealed scores and other-side private state
  • Raw judge inputs that would leak the suite
Judge sandbox

Execution has no trust

  • No network and no service credentials
  • CPU, memory, time, output, process limits
  • Scratch filesystem only; no durable state
Reconnect

Socket loss is not a leave

  • Place remains reserved until match end
  • Grace window restores a filtered snapshot
  • Unacknowledged actions are not replayed
Scaling note

Realtime is single-instance today

  • Socket fan-out and chat history are process-local
  • Postgres-backed HTTP actions survive instances
  • Sticky sessions or pub/sub are needed to scale sockets
Review rule: a UI hiding a field is not access control. Filtering must happen in the Game service snapshot, gateway authorization, and direct-request tests.

One-minute explanation

“Code Arena is a real-time coding battle. The browser is only a client. Game owns the match state and score, the judge executes untrusted code in a sandbox, and Postgres stores durable truth. Core owns identity and Game owns match-scoped chat. The diagram separates what our repository proves today from what we still need to integrate before claiming the final ft_transcendence modules.”

Then walk the arrows from Browser → Nginx → Game → Judge → Game → Reveal.

Why not let the browser calculate the score?

Because a browser is controlled by the player. The server must receive the action, validate it, persist it, and own the reveal.

Why is the judge separate?

Player code is untrusted. Isolation limits CPU, memory, time, output, processes, filesystem, and network access without exposing service credentials.

What makes 2v2 different?

Two teammates share one team document and must both be Ready for the current revision. Collaboration traffic stays separate from game authority.

What should we not claim yet?

Do not present Core auth, durable Game-owned chat, Compose judging, or final module completion as finished until their acceptance evidence exists.

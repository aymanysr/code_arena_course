Chapter 1 · Follow one Match / Lesson 01 of 14

Follow one Submit.

Trace what happens when a player submits code. Your goal: know who sends the request, who decides whether it is allowed, and who runs the code.

YOUR PLACE IN THIS LESSONSTEP 1 OF 4

01 / Make a prediction

Who has the final say on whether Submit is allowed?

A button can be disabled in the browser, but that alone cannot protect a game rule. Choose the layer you think has the final say. Then follow the request and see where the decision happens.

Your guess is a starting point, not a gate. You can open the trace without answering.

02 / Follow the request

A click starts the request. The Game owns the rule.

Follow the same piece of work across four boundaries. The browser starts it; the Match engine authorizes it; the Judge executes only after that handoff.

  1. 01

    The toolbar offers Submit

    EditorToolbar disables the button for obvious UI conditions and calls its submit callback. That improves the screen; it is not the security boundary.

    Open EditorToolbar.tsx · line 46 ↗
  2. 02

    The workspace sends the current code

    CodeWorkspace passes the live editor content and language to the transport's submit() request. The view does not decide whether the Match accepts it.

    Open CodeWorkspace.tsx · line 87 ↗
  3. 03

    ArenaEngine checks the Match

    The engine resolves the member and current Round, checks expiry and the phase/readiness rules, rejects while Reveal is closing, and records the accepted evaluation request.

    Open engine.ts · line 511 ↗
  4. 04

    The Judge executes submitted code

    Only after the Game accepts the request does evaluation run through the Judge boundary. The Game remains the authority for Match rules and scored state.

    Open engine.ts · line 669 ↗
Keep the responsibilities separate: Editor → Transport → ArenaEngine → Judge. A client request asks; the server decides; the sandbox runs.

03 / Check the evidence

A test checks that the Match rejects a late Submit.

Read one concrete case. Ask what it demonstrates—and what you would still need to test in a rewrite.

Reference test · observed behavior

After Reveal, another Submit is rejected

The test submits once, publishes Reveal, then expects a later Submit to reject. That supports the claim that the engine enforces the post-Reveal boundary, even if a client tries to call it again.

Open submit-path.test.ts · line 215 ↗

What this test does not prove: every possible authorization rule, sandbox isolation against all attacks, or parity in your future rewrite. It is evidence for this specific late-Submit case.

04 / Retrieve it from memory

Explain the path without looking back.

Try saying it aloud, or jot down a few words. You do not need to get it perfect.

  • Which layer decides if this Match can accept Submit?

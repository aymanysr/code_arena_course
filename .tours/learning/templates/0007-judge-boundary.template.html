First, make a prediction

The Judge runs submitted code in Docker. Does that automatically keep hidden test cases secret from that code?

Also ask: who decides whether the player is allowed to Submit—the Game or the Judge?

Check your prediction

The Game authorizes and records the action; GameJudge executes code and returns verdicts. Container limits can restrict resources and network access, but that alone does not prove that test data is hidden from the submitted program.

Now follow the trust boundaries

“Not sent to the browser” and “secret from the program” are different guarantees

  1. 01

    The Game chooses the judge; the interface only defines execution

    GameJudge has two jobs: run visible tests and evaluate sealed groups. It owns no Match state, score counting, or Reveal. The Game service currently defaults to ContainerJudge; JUDGE_BACKEND=judge0 selects the optional Judge0 adapter, which requires its configured URL. It does not silently switch providers.

    Execution-only contract · judge.ts:107 Default ContainerJudge and optional Judge0 wiring · game.service.ts:145 Visible and sealed methods share the adapter · container-judge.ts:196 Judge0 stays behind the same interface · judge0.ts:88
  2. 02

    The container has useful resource restrictions

    The current Docker command drops capabilities, disables networking, sets CPU/memory/process limits, uses a read-only root filesystem with temporary scratch space, and runs as nobody. These are meaningful containment controls. They are not proof that an attacker cannot read data that the runner itself places inside the job.

    Current Docker job flags · container-judge.ts:260 Compile/run script and per-case execution · container-judge.ts:346 Missing launcher is infrastructure failure, not a verdict · container-judge.test.ts:62
  3. 03

    Current source suggests hidden cases are readable by submitted code

    Security caveat: source-review inference, not an executed exploit

    The current job passes base64-encoded INP/EXP case blobs as environment variables and materializes input/expected files under /scratch. For Python snippets, the runner imports the submitted module into the Python driver process that reads those files. For standard-input programs, the compiled program runs as the same job user in that directory. From these code paths, untrusted submissions appear able to inspect or decode the hidden-case blobs. Base64 is encoding, not encryption. No malicious program was run as part of this lesson work.

    The game-level sealing test still matters: it checks that raw hidden material is absent from snapshots, receipts, events, and Reveal. But that is the browser boundary; it does not test whether contestant code inside the Judge job can read its own environment/files.

  4. 04

    Evidence has scope—and some suites could not run here

    The Docker security tests exercise resource attacks, filesystem behavior, egress and cleanup; the environment test does not check case-blob confidentiality. Judge0 unit tests use a scripted HTTP client, so they verify adapter mapping and limits, not a deployed Judge0 service or its isolation. The isolation decision/results are a dated Linux/aarch64 spike record, not a current run of the production code.

    This session cannot access the Docker socket, so the real-container suites are not counted as passing here. The missing-binary unit test can still validate the error classification without launching a real container.

What the evidence can—and cannot—support

Supported by source and the sealing test

The default implementation uses a Docker job with concrete resource/network restrictions. The engine-facing test checks that raw hidden markers do not appear on client DTO/event/reveal surfaces.

Not established

This task did not execute Docker tests; old spike measurements do not substitute for current runtime evidence; and neither those controls nor the client-boundary test establish secret hidden cases against hostile submitted code. Keep that confidentiality claim unresolved until isolated by design and a malicious-code regression.

Why the course records the caveat

This is a current-source observation for learning, not an implemented fix or a new 42-subject module claim. Do not treat the existence of a “sandbox” as proof of every security property.

Check the model in your head

Which layer rejects an illegal Submit, and what separate question must the sandbox answer?

Name both the game-rule boundary and the hostile-code boundary.

Show a useful answer

The Game engine decides whether Submit is legal and updates Match state. The Judge only executes code and returns verdicts. Separately, the execution environment must prevent untrusted code from reading host secrets, escaping resource limits, reaching forbidden services, and learning hidden test inputs/expected values. The current source supports some of those controls but does not establish all of them.

Rewrite-test prompt

First add a hostile Python and compiled-program test that attempts to inspect every environment variable and file available to the submitted program, then verify it cannot recover any hidden input or expected value. Keep this separate from tests for network denial, resource limits, filesystem escape, and “no host credentials.” Run those attacks against the actual container configuration, and do not claim confidentiality until the case data is outside the contestant-readable process/filesystem boundary.

Now follow the request

One Submit crosses several small boundaries

Follow the links in order. Each source opens at the relevant lines. The UI asks; the server decides; the judge executes.

  1. 01

    The editor turns your click into an action

    EditorToolbar calls its onSubmit callback. CodeWorkspace supplies the current code and language to the transport. The screen starts the request; it does not authorize the match action.

    Button callback · EditorToolbar.tsx:46 Current code → transport · CodeWorkspace.tsx:88
  2. 02

    The live transport sends an HTTP request

    ArenaTransport defines what submit() means to the UI. The live SocketArenaTransport sends POST /submit and includes stable IDs so a retry can refer to the same logical attempt.

    Transport contract · transport.ts:84 Live adapter · socket.ts:450
  3. 03

    The HTTP controller checks the request shape

    GameController gets the signed-in player, checks basic input limits, then forwards the request. It is the front door—not the referee for round state, score, or membership.

    Submit route · game.controller.ts:83
  4. 04

    The application service wires the call onward

    GameService turns the user ID into a trusted principal and calls ArenaEngine.submit(). It can also trigger a reveal after the accepted result satisfies the reveal condition.

    Submit forwarding · game.service.ts:230 Configured judge · default is ContainerJudge
  5. 05

    The engine applies the game rules and records the attempt

    Under the match lock, ArenaEngine checks membership, phase, time, language, and (for 2v2) the current team-ready document. It records a pending submission before asking for a verdict. That makes game authority separate from the UI.

    Submit checks · engine.ts:511 Pending record · engine.ts:607 Hand off for evaluation · engine.ts:669
  6. 06

    The orchestrator owns evaluation work; the judge owns execution

    EvaluationOrchestrator claims the pending evaluation so retries do not create duplicate work. It calls the GameJudge contract. The default ContainerJudge runs the hidden tests in a restricted Docker container; Judge0 is an optional configured adapter.

    Claim and evaluate · evaluation-orchestration.ts:172 Judge contract · judge.ts:107 Container judge · container-judge.ts:221

Keep these three jobs separate

Transport: deliver an action. ArenaEngine: decide whether the action is legal and change match state. Judge: run untrusted code and return verdicts. The test below uses a fake judge to check engine behavior, so it is not itself proof of Docker security.

Check the model in your head

The controller accepts the request shape, but the round is already closed. Who rejects Submit?

This is the useful distinction: receiving a request is not the same as deciding whether a game action is legal.

Hint: which component has the current round phase?

The path, from memory:

EditorToolbar → CodeWorkspace → live transport → GameController → GameService → ArenaEngine → EvaluationOrchestrator → GameJudge

The engine enforces the match rules; the judge only runs the program. In this version, ContainerJudge is the default implementation, and Judge0 can be selected by configuration.

Why this is a good first slice

For your rewrite

You do not need to recreate these class names. First preserve the observable contract: a valid player can submit at the right time; an invalid action is rejected; accepted code is evaluated once; the result is returned without leaking hidden tests.

For this course

CodeTour gives you editor navigation; the source map tells you what is still uncovered; these short lessons give you a chance to predict, inspect, and explain one real behavior. A green test in this repository is evidence about this implementation—not automatic proof that a separate rewrite matches.

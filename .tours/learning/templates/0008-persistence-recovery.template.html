First, make a prediction

The Game service restarts halfway through a Match. What can it pick up again?

Before opening the answer, sort these into “durable record,” “reconstructed at boot,” or “gone with the old process”: the Match score, a pending Submission, socket Presence, and an in-flight JavaScript promise.

Check your prediction

With DATABASE_URL configured and the Postgres volume intact, Match and Submission records are durable. Boot recovery resets Presence to offline and re-drives pending Evaluations. A JavaScript promise/in-flight registry is process-local and is not restored. Without DATABASE_URL, the service builds fresh in-memory stores, so those records are not durable across a restart.

Key terms

MatchPersistence
The domain-shaped interface the Arena engine uses to load/save Matches, Submissions, Reveals, and team documents.
Postgres store
The configured adapter that saves those records in the database; the Compose stack gives Postgres a named data volume.
Boot recovery
Work the Game service awaits after creating its engine and before it starts serving.
Process-local state
Memory owned by one running Node.js process, such as an in-flight promise or socket connection.

Now follow one restart

The answer depends on which store the Game service actually selects

  1. 01

    Startup chooses the storage adapter

    If DATABASE_URL exists, the service creates PostgresStores, ensures the Game schema, and gives its persistence interface to ArenaEngine. Without the variable, it creates new in-memory Maps. The Compose Game service supplies a database URL; the Compose Postgres service mounts a named volume. The init script creates service databases/roles on first volume initialization; PostgresStores.ensureSchema() creates the Game tables.

    That means “we use Postgres in Compose” and “a local run has durable storage” are not automatically the same statement. Check the actual process environment.

  2. 02

    Postgres stores the current Match record as JSONB

    The matches table has an ID plus a data JSONB value. Saving writes the Match record and its Round/side summaries inside a transaction, with an optional revision check. Separate tables hold Submission JSON, published Reveal JSON, and shared team-document state. The existing JSONB shape is left untouched by this course task; this code path is not evidence of arbitrary forward/backward migration compatibility.

    MatchAuthority serializes a short Match change, stamps its revision, then asks the persistence interface to save it. The storage interface hides which adapter is underneath, but that interface alone does not make the in-memory adapter durable.

  3. 03

    Before serving, boot recovery repairs what a process cannot carry forward

    The Game service awaits engine.recover() before it accepts traffic. Recovery loads known Match IDs, marks their participants offline with a fresh reconnect grace period, repairs transient activity labels, restores an interrupted Reveal when its durable record exists, and then recovers pending Submissions.

    A pending Submission row is durable work. The Postgres adapter claims it with a database-session advisory lock and commits the terminal Submission plus Match under that claim. If the process and database session disappear, that lock is released; recovery can claim and re-drive the still-pending row using its original IDs. The in-flight promise registry itself is process-local—recovery does not resurrect the old promise.

  4. 04

    Read each recovery test for the storage it really uses

    The reconnect recovery tests exercise recovery logic with in-memory stores shared by test engines; they are useful for the algorithm, but do not prove a database process restart. The Postgres suite creates new engines over the same database and covers a completed retry, an unclaimed pending Submission, a persisted Reveal, and Match clock/count restoration. That is the direct database evidence—when the suite actually runs.

What survives—and what gets rebuilt?

With Postgres configured and its volume intact

  • Match/Round state, counted results, and Submission rows are stored.
  • Completed request retries can return their stored outcome.
  • Pending Evaluations can be found and re-driven.
  • Boot sets Presence offline and starts a fresh reconnect grace window.

Not carried across a process restart

  • JavaScript in-flight promises and the local orchestration registry.
  • Live sockets; Presence is reconstructed as offline, not restored as online.
  • Any records held only by the in-memory adapter.

Boundaries: this lesson changes no game behavior or database schema. A named volume is not a backup, removing/reinitializing the volume changes the durability story, and the cited code does not establish a migration policy for old JSONB records.

Check the model in your head

Why does the service mark every player offline if the Match itself survived?

Answer using the difference between a saved Match fact and a live connection.

Show a useful answer

The database preserves the Match record, but a socket belongs to the old running process and cannot be resumed by reading JSONB. Boot therefore reconstructs a safe Presence state: offline, with a new grace period for reconnect. Likewise, a durable pending Submission may be retried, but its old in-flight promise is gone.

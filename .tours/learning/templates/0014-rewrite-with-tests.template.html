Check your prediction

Only the third answer. The original repository is the reference for expected behavior. Its test does not run against a separate rewrite unless you deliberately port or reproduce that test there and execute it there. Reading source, copying code, a manual click, or a green reference test is not a rewrite pass.

Key terms

Reference baseline
The exact reviewed source snapshot plus dated test evidence. This course pins current file hashes; older test results keep their original dates and environment labels.
Parity gate
A behavior-sized test in your rewrite that uses the same inputs and compares visible outcomes: accepted/rejected actions, snapshots/events, scores, and data that must stay private.
Fake
A controlled test substitute. It can test the rule or adapter contract that calls it; it cannot prove a real Docker container or PostgreSQL server behaved correctly.
Skipped / not run
Evidence is still open. A skipped test and a test file that merely exists are not a pass.

Turn the reference into your rebuild recipe

Write a failing behavior test before you implement each slice

  1. Freeze and label the target. Use this reviewed source snapshot. Keep spec/code differences visible: public 1v1 queue, the different 1v1 versus 2v2 grace-expiry behavior, and process-local team-chat history.
  2. Build the small domain core. Match creation, Round phases, score, and transitions; use a fake clock and deterministic fake Judge.
  3. Add Run, then Submit. Test visible feedback separately from counted results; then cover request identity/retries, hidden evaluation, cutoff, score, and immutable Reveal.
  4. Add Lobby and authority boundaries. Test membership, rooms/queue, admission races, who can start, and who can act before wiring more UI.
  5. Add persistence and recovery. Port in-memory contracts first; then run equivalent Postgres restart/concurrency tests against a disposable database.
  6. Add frontend and transport. Render authoritative snapshots, send commands, then verify service and real-browser flows.
  7. Add 2v2, shared editing, readiness, and team chat. Test four distinct users, revision-bound approval, team isolation, reconnect, and the current chat lifetime.
  8. Finish with real infrastructure gates. Run Docker sandbox and full browser matrices in their intended isolated environment. Keep source inspection, unit fakes, Postgres, Docker, and browser results as separate checkboxes.

The parity rule

For every gate, reuse the same starting state, inputs, and fixed clock when practical. Compare externally visible results—allowed/rejected action, receipt, snapshot/event, score, and private data—not class names. PASS only when the equivalent test in your rewrite ran and passed. Not ported, manually inspected, skipped, or only green in this repository means NOT VERIFIED.

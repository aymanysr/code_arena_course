First, make a prediction

Both Alpha teammates are Ready on document revision 1. One teammate edits the shared code. What changes?

Decide what happens to the document revision, each teammate's Ready state, Beta's document, and a repeated copy of the same Yjs update.

Check your prediction

If the accepted update changes the actual source text, Alpha advances to revision 2 and both Alpha approvals are invalidated. Beta has a separate team document, so it is not changed by Alpha's edit. A duplicate update that changes no source text does not earn another application revision. Both Alpha players must approve revision 2 before their team can Submit.

Key terms

Yjs document
The shared CRDT state used to merge teammates' text edits. A Yjs update frame is not itself the game's approval number.
DocumentRevision
A monotonic, team-and-Round-scoped number for the current shared document. In this code it is an application identity, not a Yjs state vector.
Readiness
Each member approves a particular document revision. An approval for revision 1 cannot authorize a changed revision 2.
Authoritative submission source
The server-owned team document at the approved revision. For 2v2, the Judge receives this source rather than trusting the browser's code field.

Now follow one accepted edit

One edit crosses a collaboration channel and a game-rule boundary

Follow these small steps in order. The collaboration socket carries shared text; the Game engine remains the authority for revisions, readiness, and Submit.

  1. 01

    The browser sends a Yjs update, not permission to Submit

    CollabClient watches its shared Y.Doc and emits incremental updates on the separate /collab namespace. The gateway verifies the trusted socket principal and asks the Game to sync before joining a server-derived team room. A room name or user ID supplied by the browser does not choose which team's document it may access.

    The game socket still owns Match phase, readiness, and Submit. Keep the two channels straight: a text update changes shared data; it does not make either teammate Ready.

  2. 02

    The Game distinguishes a new source from a replay

    CollabDocs applies the CRDT frame and compares the source text before and after. If the source did not change—for example, a duplicate frame—changed is false, so the application revision does not advance just because another network frame arrived.

    For a real source change, TeamCollaboration checks team mode, Coding phase, membership, and the current Round; then it increments that side's DocumentRevision, invalidates both members' approvals, and persists the Match plus team document. If persistence fails, its rollback path restores the previous document, revision, language, and readiness.

    Yjs update count is not the application revision

    The revision represents the current team document version used by readiness and Submit. Awareness/cursor messages are separate ephemeral signals; they are not edits and do not make the document revision advance.

  3. 03

    Both teammates approve the same current revision

    Readiness is stored per user on the current Round, with the approved document revision. The Game rejects a Ready request for an old revision. After an accepted edit changes revision 1 to revision 2, both team members become not-ready; they must each approve revision 2.

    The checkbox and disabled Submit button are helpful UI feedback, not the security or game-rule boundary. ArenaEngine repeats the checks while holding the Match lock.

  4. 04

    Submit freezes the server-owned source

    Inside the Match lock, the engine checks the team's Ready gate and current revision. For 2v2 it asks TeamCollaboration for the shared source at that revision and replaces the browser's submitted code with that server-owned text before validation and judging.

    An edit racing with Submit has one whole outcome: Submit freezes the old approved revision before the edit, or the edit advances the revision first and makes old readiness stale. The race must not combine old approval with new code.

Close the source and recall

Can you explain why editing makes both teammates Ready again?

Hint, then check yourself

State the chain in order: changed shared text → new application revision → invalidate both approvals → both approve that same revision → server checks and freezes that source. A repeated frame with no text change is not a new application revision.

Rewrite-test prompt

In your rewrite, test one accepted source edit after both teammates approved revision 1. Assert the shared text is revision 2, both approvals are invalid, a revision-1 Submit is rejected, and Submit becomes possible only after both members approve revision 2. Also assert the Judge receives the server document rather than a deliberately different client code payload; duplicate updates do not bump the application revision; and an edit racing with Submit yields either a fully frozen old revision or a stale-approval rejection, never a mixed state. Add a persistence-failure case using a disposable database before claiming transaction rollback.

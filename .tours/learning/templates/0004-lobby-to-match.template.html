First, make a prediction

A 1v1 invite room has two players and both are Ready. Can the guest start—and can either player submit immediately?

Write down who has permission to start, what still has to be created, and which part of this decision belongs to the server.

Check your prediction

Only the room host may start. The server rechecks membership, full sides, and everyone's readiness even if the UI button is enabled. Starting creates a Match in MATCH_FOUND; the first Round still needs its own start action before coding can begin.

Now trace the boundaries

A Lobby groups players; the Game service creates the Match

The screen collects choices and displays membership/readiness. The backend checks those choices and owns the resulting Match identity.

  1. 01

    The screen asks the Lobby client to act

    LobbyPage handles the clicks. LobbyClient turns them into HTTP requests such as /lobby/rooms, /lobby/rooms/join, /ready, and /start. The button can guide the player, but it is not the authority.

    Create / join / ready / start handlers · LobbyPage.tsx:90 UI's host-and-readiness display gate · LobbyPage.tsx:170 Lobby HTTP client · lobby.ts:84 Backend room routes · lobby.controller.ts:38
  2. 02

    There are two current ways to gather players

    Private room: the host creates an invite code; players join it and see the room's members, sides, and Ready flags. For 1v1, host starts Left and the guest joins Right. In 2v2, each side needs two members.

    Public queue: a waiting entry is matched when enough players of that mode are available (two for 1v1; four for 2v2). The current matcher orders waiting rows by join time, creates the Match, then marks queue entries matched.

    Public queue matching · lobby.ts:291 Create private room · lobby.ts:357 Join private room by code · lobby.ts:426 Two-player queue case · lobby.test.ts:67 Four-player queue case · lobby.test.ts:109
  3. 03

    The server checks who may see the room and who may start

    Room reads and room socket subscriptions are for members only. To start a private room, the backend checks that the caller is the host, every player slot is filled on the correct sides, and every member is Ready. A direct HTTP request gets these same checks; bypassing the disabled UI button does not bypass the rule.

    Authorize room membership · game.service.ts:364 Authorize live room subscription · lobby.gateway.ts:65 Private-room start route · lobby.controller.ts:95 Host, capacity, and Ready gate · lobby.ts:685 Gate tests for host / fullness / Ready · lobby.test.ts:215 Non-members cannot read or subscribe · lobby.test.ts:68
  4. 04

    Game creates a Match, then tells the players to enter it

    GameService selects the problem versions and calls ArenaEngine.createMatch() with the mode and participant-to-side mapping. The private room becomes matched, and a member-targeted lobby.matchFound event carries the new Match ID. The Match begins at MATCH_FOUND; the first Round has not started yet.

Current code and intended first-release scope disagree about Quick Play

Keep this discrepancy visible

The current UI, Lobby service, and queue tests include automatic public matchmaking. But .scratch/code-arena/spec.md:19 says invitation-code rooms are the first-release entry and automatic matchmaking is not in scope. This course records what the checked code currently does; it does not approve expanding release scope or claim that the spec has been updated. Resolve that product decision separately before treating Quick Play as intended release behavior.

There is also a development-auth boundary: this Lobby client sends an x-dev-user-id header, which the Game service reads through its development principal seam. That is not evidence of the finished signup/login system.

Check the model in your head

Everyone is Ready, but the guest sends POST /lobby/rooms/:id/start directly. What happens?

Answer before opening the hint. Include the part the UI plays and the separate check the backend must perform.

Show a useful answer hint

The backend rejects the guest because only the room owner can start. The UI's disabled button is just guidance; the domain gate also verifies capacity and readiness before it asks the Arena engine to create the Match. Then the Match is in MATCH_FOUND, waiting for the first Round to begin.

Rewrite-test prompt

Write separate tests for the boundary and the rule: a non-member cannot read or subscribe to a private room; a non-host cannot start; a host cannot start while slots are empty or someone is not Ready; a valid host request creates one Match only. For the public queue, first decide whether that behavior belongs in your approved product scope.

Closing, cutoff, Reveal: when an in-flight result counts

In about 8 minutes: Predict which in-flight Judge result can count, then trace how a Round closes, waits, cuts off late work, and freezes its Reveal.

First, make a prediction

The Judge is still working when Reveal starts. What happens to its result?

Imagine the Judge returns once during the grace window, and once after the cutoff. Write down whether each score appears in Reveal before opening the explanation.

Show the prediction to check

A result that settles during grace can count. A result still unfinished at cutoff is superseded: its verdict cannot change the score frozen into Reveal. New submissions are rejected as soon as the Round starts closing.

Now trace four moments

Closing is not the same moment as publishing

Follow the source links in order. This is one current implementation path; the tests below check the important timing cases.

  1. 01

    The Round starts closing

    ArenaEngine.publishReveal() asks RoundLifecycle to set closing, then saves that state. This closes the door to new Submissions, but it does not yet publish a score or change the Match phase.

  2. 02

    Already-running evaluations get a grace window

    The engine waits for the in-flight Judge promises to settle, or until the configured grace time runs out—whichever happens first. A verdict that settles in time can still become the Round's counted result.

    Find pending work and wait · engine.ts:699 Verdict inside grace counts · scoring-reveal.test.ts:86
  3. 03

    The cutoff separates counted work from late work

    After the wait, prepareReveal() marks the cutoff and identifies unfinished evaluations. When one returns too late, evaluation orchestration stores it as superseded and does not replace the counted result.

    Mark cutoff and pending IDs · round-lifecycle.ts:83 Count only before cutoff · evaluation-orchestration.ts:432 Late verdict stays out of score · scoring-reveal.test.ts:109
  4. 04

    The engine freezes and publishes the Reveal

    It builds scores from the results already counted, creates a frozen snapshot, persists it, then commits it to the Round. Only that final commit moves the Match into the Reveal phase. A later Judge result cannot rewrite the published scores.

Three words that are easy to mix up

closing

New Submissions are no longer accepted. Existing evaluations may still finish during grace. The phase can still be CODING.

Cutoff

The grace wait has ended. Unfinished evaluations are superseded and cannot affect the score for this Reveal.

Published

The authoritative snapshot has been persisted and committed. That is when the phase changes to Reveal.

Immutable snapshot

The stored score and breakdown stay fixed. A caller can edit its own returned copy; that does not edit the saved Reveal.

What this test file does not prove

These cases do not measure real Docker/Judge timing under load or prove every possible race is impossible. They use a controlled fake Judge to check these particular state rules. Container isolation is a different question and has its own tests.

Check the model in your head

The Round says closing, but the phase still says CODING. A Judge result arrives after cutoff. Can it change the Reveal?

Answer in your own words before opening the hint. Explain what happens to new Submissions, in-flight work, and the saved score.

Show a useful answer hint

No. Closing rejects new Submissions but gives existing work a short grace window. Once the cutoff passes, unfinished evaluations are superseded. The engine builds and persists the Reveal from counted results, then commits the phase change. The late verdict cannot rewrite that snapshot.

First, make a prediction

You edit a solution and press Run. Does that test the hidden cases or change your round score?

Before opening the hint, write down where the problem and starter code come from, then guess which tests Run sends to the judge.

Check your prediction

The problem bank supplies the prompt, examples, starter code and separate visible/hidden suites. The current editor begins with your saved local draft or the selected starter. Run sends that code through the visible suite and updates test status; it does not create a scored submission. Submit is the path that evaluates the sealed hidden suite.

Now follow the data and the action

Problem data, editor draft, and Run are three different things

Follow the links in order. We are tracing the checked problem records and live frontend—not treating the frozen prototype/game-ui/09-arena.html interaction reference as runtime evidence. Notice both what is present and what the current code leaves out.

  1. 01

    A checked JSON record defines the challenge

    The problem schema requires a statement, examples, constraints, language starters, visible tests, hidden groups, and provenance. In Even Ledger, the public examples explain the task; the visible suite has three small cases; the hidden groups cover additional inputs and contribute weights during scoring.

    Double It is a different execution shape: its record declares a standard-input program. The data format describes what to run; it is not itself the screen or the judge.

  2. 02

    The server snapshot gives the Arena its public problem view

    FileBank maps the record into a statement, examples, starters, and separate visible/hidden collections. The engine snapshot sends title, description, examples and starters, plus visible test inputs. It does not send the hidden groups.

    A real gap in the current screen

    The JSON schema requires constraints, and Even Ledger has them, but FileBank does not put constraints in its returned statement. The public snapshot type and current ProblemPanel therefore cannot display them. This is evidence about the current code—not a claim that the constraints are absent from the problem record.

  3. 03

    The editor works with a draft; the toolbar chooses the action

    For a local 1v1 editor, ArenaPage starts from this round/problem/language's saved browser draft or the starter, then stores edits in local storage. In live 2v2, the shared document is authoritative instead. EditorAdapter hides CodeMirror behind a small editor contract. CodeWorkspace reads the current source and language for either Run or Submit.

    One UI detail to inspect: TestPanel's “Custom input” box only updates its own component state. It is not passed to the transport, so pressing Run still sends the editor source against the full visible suite; the box does not currently execute that typed input.

  4. 04

    Run travels to the visible suite; Submit takes the scored path

    The live transport posts Run to the Game endpoint. The controller checks the request shape, the service delegates, and ArenaEngine.run() authorizes the player and phase, then passes only problem.visible to the judge. It records visible statuses for the panel and returns the side to coding. It does not count a submission, change the score, or publish Reveal.

    Submit is different: its evaluation is prepared with the hidden groups. Client-facing tests check that hidden input and expected values do not leak into snapshots, receipts, events, or Reveal (Reveal publishes group results, not the raw cases).

A green Run is a clue, not a guarantee

What visible tests tell you

Your current code passed the public cases that Run exercised. This helps catch mistakes quickly, but hidden groups can still find edge cases or produce a lower score at Submit.

What each test proves

run-path.test.ts uses the engine's test setup to check routing, state, and suite separation. compiled-bank.test.ts is the end-to-end path using real records and isolated containers. Do not treat a unit test with a fake judge as evidence that the container sandbox itself is secure.

Show a useful answer

The server snapshot supplies the selected starter and public problem fields; the editor keeps the current local draft (or the shared 2v2 document); Run sends that source and language to the Game service, which asks the judge to run the visible suite only. Submit follows the separate hidden evaluation and scoring path.

Rewrite-test prompt

In your own implementation, test these contracts separately: (1) a selected problem provides a language starter; (2) editing updates the source used by Run; (3) Run executes visible tests and updates only visible statuses; (4) hidden inputs never appear in the client snapshot; (5) Submit evaluates hidden groups and is the action that can produce a score. Add a test for constraints if you decide they should appear in the prompt.

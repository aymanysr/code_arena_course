Team chat is a side channel—not editor state or Match state

In about 10 minutes: Trace a 2v2 team message through its authorized room, understand what chat cannot change, and distinguish Match-scoped chat lifetime from Round-scoped collaboration.

Source references match 10 pinned files Snapshot 4edc506dd9158d21

1 · Predict → 2 · Trace → 3 · Recall

First, make a prediction

A2 sends Alpha a “Ready?” ping. Does A2 become Ready? What will a reconnect recover?

Before opening the code, decide who can see the ping, what game state it can change, whether chat survives a Round change, and whether its server history survives a Game-process restart.

Check your prediction

The ping is a chat entry delivered to Alpha's team room; it does not approve the shared document or mutate Match readiness. Chat belongs to the Match, while the shared document belongs to a Round, so a Round change replaces the collaboration client but preserves chat. The Game server keeps at most 25 recent entries per team room in process memory: reconnect can reload them while that process is alive, but a Game restart loses the server-side history. A page that has not reloaded may still have its own already-received messages in browser memory.

Key terms

Team room
A server-authorized Match-and-side channel. Teammates share a room; the opposing side uses another room.
Chat entry
A text message or contextual quick ping. A ping labeled “Ready?” is communication—not the gameplay Ready action.
Process-local history
Recent messages held in a Game-service memory map. Reconnection can retrieve them from the same process, but this is not database persistence.
Sidecar lifetime
A browser-owned client that lives alongside Arena transport. Team chat is Match-scoped; collaborative editing is Round-scoped.

Now follow one team message

Chat communicates beside the Match; it does not become Match state

Keep three channels and two lifetimes separate: the Game namespace owns Match rules, /collab carries the Round's shared document, and /chat carries Match team messages.

  1. 01

    The browser connects to the Game service's chat namespace

    TeamChatClient opens /chat, waits for authorization, and listens for history, messages, and pings. The shared types distinguish ordinary text from a small set of contextual quick pings. This chat gateway lives in the Game service; it is not the deferred standalone Chat service. As Lesson 9 explains, the current principal is a development-only identity seam—not production login.

  2. 02

    The server resolves the member's team room

    The gateway derives identity from the trusted socket principal and asks the Game service to resolve the caller's Match membership and team side. It joins the server-derived room before sending any recent history. A stranger or a 1v1 player is not granted a 2v2 team-chat room, and client-supplied sender/side fields are not authoritative.

    A valid message is trimmed, bounded, associated with the authenticated user and side, added to that room's recent history, then broadcast to that room only. Retry IDs can return the original message ID instead of broadcasting a second copy.

  3. 03

    A chat event cannot approve code or edit the document

    The gateway documents the boundary directly: messages and pings do not call the Arena engine, touch Y.Doc, bump DocumentRevision, or toggle readiness. A “Ready?” ping is just text with a label. The actual Ready action still belongs to the game transport and is checked by the Game rules.

    The TeamChat component is a separate status-and-message panel. It subscribes to its chat client; the collaborative editor has its own Round-scoped client from Lesson 10.

  4. 04

    Chat survives a Round transition, but not a Match change

    The sidecar manager builds the collaboration key from the Round and its connection config, so a new Round disposes the old collaboration client and makes a fresh one. The chat key uses its config without the Round: the same chat client stays connected. Changing Match/transport identity or disposing Arena disconnects both.

    Do not confuse that client lifetime with durable chat history. On the server, the newest 25 entries per room live in an in-memory Map. A reconnect to the same running Game process can receive them; a process restart clears that map. An already-open browser may still display entries it had received until that client is replaced or the page reloads, but there is no durable history store here.

What the tests show—and what they do not

Frontend tests: the chat-client unit test checks message-ID deduplication and local status; sidecar tests check that a Round swap preserves chat while replacing collaboration, and that Match changes dispose both. Those tests do not open a real socket or prove server history persistence.

Service and browser scenarios: team-chat.test.ts and live-team-chat.spec.ts contain authorization, four-player team isolation, ping/readiness separation, retry, reconnect-history, and editor/chat coexistence scenarios. They are linked as test source, not as runs from this lesson. The service suite starts a local listener; socket suites in this environment have already failed to bind with listen EPERM, so this suite was not run. Playwright was not run.

Persistence limit: source shows an in-memory bounded history map and no durable chat-history adapter. The test source restores recent history on reconnect within the running process; it does not establish history recovery after service restart.

Close the source and recall

What disappears at a Round boundary, and what disappears at a Game restart?

Hint, then check yourself

Name the owner and lifetime: the shared document client is keyed by Match plus Round; chat client is keyed by Match; server-side recent chat history is a bounded process-memory map. A Match change disposes both browser clients. A Game restart empties the server map, even though an already-open page may still hold entries it previously received.

Rewrite-test prompt

In your rewrite, connect four users and show that an Alpha message reaches only Alpha; forge sender/side fields and assert the server derives identity; send a “Ready?” ping and assert gameplay readiness is still false; retry one message ID and assert one teammate-visible entry; then disconnect/reconnect and assert the room's recent history is restored while the process is alive. Separately assert that changing Round replaces only the collaboration client, changing Match disposes both, and restarting the Game loses server-side chat history unless you deliberately add durable storage. Keep a UI click or mock transport separate from server authorization evidence.

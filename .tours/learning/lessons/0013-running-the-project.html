The local play script and Compose stack are not the same thing

In about 10 minutes: Trace the two supported local run paths, identify what each service currently owns, and use the setup files without mistaking scaffolding for product behavior.

First, make a prediction

If you run npm run up, where does the React game screen come from?

Choose before tracing: Compose starts a frontend container; Nginx serves the frontend; the frontend is not in this Compose stack; or the separate Chat container renders it.

Check your prediction

The frontend is not a service in the current docker-compose.yml. Compose starts PostgreSQL, Redis, Core, Game, the deferred Chat skeleton, and Nginx. The separate scripts/play.sh path builds the Game and frontend, then serves the frontend preview. These are different local workflows; neither is a production deployment proof.

Key terms

Workspace
The root npm project groups packages, services, and the frontend so shared modules can be built and tested together.
Compose service
A local container role with its own build or image, environment, network dependencies, and optional health check.
Liveness
“Is this process answering?” The current /health route reports process/model information; it does not prove the application is ready to serve gameplay.
Readiness
“Can required dependencies be reached?” The current /ready route checks TCP reachability for PostgreSQL and Redis. It is a separate route, not a gameplay test.
Judge Worker readiness
The worker readiness checks Docker and required images through its separate /ready route. Game's health/readiness routes check Game dependencies instead.

Now trace two local run paths

A local command is not automatically the same stack as Compose

  1. 01

    The root package is the command directory

    The root manifest declares three npm workspace groups: packages/*, services/*, and frontend. Its aggregate scripts delegate test, typecheck, lint, and build to workspaces. Root pretest builds the workspaces before tests run; Game service tests launch services/game/dist/main.js, so a clean checkout needs that build first. npm run certs creates local TLS material; npm run up delegates to Docker Compose. The root prepare script installs Husky with the dependencies. Before a commit, .husky/pre-commit runs staged-file formatting, typecheck, and the workspace tests. Tests that need Postgres, Docker, or local sockets still need their required environment; a blocked test is not a pass.

  2. 02

    Local play builds the web preview and starts Game directly

    ./scripts/play.sh is a convenience development script, not Compose. It builds the Game workspace and frontend, starts the Game Node process, and serves the frontend preview; its default ports are Game 3220 and web 4173. It uses HTTP for local connections; that is development-only and not evidence for the PDF's HTTPS requirement. It sets DEV_PRINCIPAL=true, so this shortcut does not represent production authentication. Its comments warn that without Postgres Game falls back to memory, and without Docker Run/Submit fail safely.

    Purpose and local/LAN modes · play.sh:2 Development database URL and Game endpoint · play.sh:17 Build and launch Game plus frontend preview · play.sh:23 Cleanup when the script exits · play.sh:30

    Read before choosing LAN mode

    The script exposes its local development server to your LAN when requested. Only use that mode on a network you trust. Its development identity seam and missing production authentication are not hidden by the UI.

  3. 03

    Compose builds the local service stack—but not the whole game

    The Compose comment gives the setup order: create self-signed localhost certificates, copy .env.example to the ignored .env, then start Compose. The services include PostgreSQL, Redis, Core, Game, the Judge Worker, the deferred Chat skeleton, and Nginx. Only Nginx publishes ports 80 and 443; there is no frontend container. Compose sets JUDGE_BACKEND=worker and the Game-side WorkerJudgeAdapter sends requests to JUDGE_WORKER_URL=http://judge-worker:3010 over the internal judge network. The worker runs ContainerJudge. Compose mounts the Docker socket into the Judge Worker only. Local direct Game runs default to ContainerJudge; optional Judge0 is another explicitly configured provider.

    The worker requires JUDGE_WORKER_TOKEN; the value in .env.example is only a placeholder. JUDGE_WORKER_TIMEOUT_MS is 930000 ms. Worker defaults are JUDGE_WORKER_CONCURRENCY=2, JUDGE_WORKER_MAX_QUEUE=8, JUDGE_WORKER_QUEUE_TIMEOUT_MS=30000, and JUDGE_WORKER_JOB_TIMEOUT_MS=900000. Its entrypoint prepares missing judge images. /health is liveness; worker readiness checks Docker and required images through /ready, and Compose waits for that readiness before starting Game. These values describe local Compose configuration, not a production capacity claim.

    The internal network keeps the worker off the public path: Nginx does not publish or proxy the worker. The Docker socket grants daemon-level authority, so a private Compose network is not proof that running hostile code is safe or isolated from the host.

  4. 04

    Follow an HTTP or WebSocket request through Nginx

    Nginx terminates HTTPS/WSS, proxies /api/core/ to Core and /api/game/ to Game, and sends Socket.IO—including Game-owned /chat—to Game. The separate Chat container is still startup/health scaffolding. The Game module wires the actual game, lobby, collaboration, and team-chat controllers/gateways; Lesson 11 follows the chat behavior itself.

    TLS listener and API proxy routes · nginx.conf:19 WebSocket ingress, including Game-owned chat · nginx.conf:35 Game module wiring and development-principal seam · game.module.ts:11

What each backend process currently owns

  • Game: the active HTTP/WebSocket application adapter; its module wires the Match, Lobby, collaboration, and team-chat paths to the Arena engine and model.
  • Core: currently a Nest bootstrap plus /health and /ready; the current module does not implement account/profile product behavior.
  • Chat container: currently a Nest bootstrap plus health/readiness scaffolding. First-release Match chat is in Game's /chat namespace, not this separate service.
  • PostgreSQL and Redis: local infrastructure dependencies. The presence of containers and health checks does not show that every feature uses them or that a production deployment has been verified.
  • Nginx: public local entry point, TLS termination, and reverse proxy; it does not render the React frontend in this Compose configuration.

Health is not the same as readiness

Each /health route answers from the process. Each /ready checks whether PostgreSQL and Redis accept a TCP connection. Compose's health checks currently call /health, not /ready. No containers were started for this lesson update, so this walkthrough reports configuration and source—not observed health responses.

Set up safely when you are ready

For Compose, first generate local certificates, then copy .env.example to .env, then use npm run up. Never copy real secrets into the example or into Git. Do not run both workflows against the same ports without checking whether something is already listening. This lesson did not start or stop Docker, alter environment files, or create certificates.

Hint, then check yourself

The convenience script builds and serves the frontend. Compose does not include a frontend container; Nginx proxies API and WebSocket traffic. The active team-chat namespace belongs to Game; the separate Chat container currently exposes only its startup health/readiness surface.

Rewrite-test prompt

In a separate rewrite, verify the advertised local command in a clean environment. Assert that the Game health route responds and that an unconfigured database does not pretend to be persistent. Then test the Compose routes and each service's actual behavior separately. Do not mark setup docs, a successful image build, or a health check as proof of authentication, chat-product behavior, judge isolation, or production deployment.

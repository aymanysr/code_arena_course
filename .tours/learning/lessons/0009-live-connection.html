Reconnecting gives you a fresh snapshot—not a frozen game

In about 10 minutes: Follow the browser's live transport through socket identity, Match membership, Presence, authoritative snapshots, and reconnect; distinguish it from service-restart recovery.

Source references match 19 pinned files Snapshot 818ea4603e970d66

1 · Predict → 2 · Trace → 3 · Recall

First, make a prediction

Your browser loses its connection during a Match. What comes back when it reconnects?

Sort these before reading on: the latest Match snapshot, your unsent editor draft, the countdown clock, your Player status, and the command you were in the middle of sending.

Check your prediction

The Game sends a fresh authoritative snapshot; the local editor draft is separate browser state. The Match clock and in-progress server Evaluation continue while the client is away. Presence changes with the socket, while Player status remains a separate gameplay state. Reconnect does not mean “replay every command that may have been sent.”

Key terms

Transport connection
Whether this browser is connected to the Game service; it is not a Match phase.
Presence
Whether a player/member currently has a live socket.
Player status
The side's gameplay activity, such as coding, running, evaluating, or locked.
Authoritative snapshot
A fresh view derived from Game-owned Match state; the browser uses it to converge after missed events.

Now follow the reconnect

The socket says who is here; Game still decides which Match they may enter

  1. 01

    The UI depends on a transport, not directly on Socket.IO

    ArenaTransport is the interface the React view subscribes to. In the live adapter, the browser first fetches a snapshot, then attaches the socket and waits for the Game's socket snapshot as its baseline. Later Game events trigger a fresh HTTP snapshot request instead of applying an event payload as a partial Match patch. Run and Submit use HTTP; some live acknowledgements, such as 2v2 readiness, use the socket.

    This keeps UI rendering based on one current server view, even if events were missed or arrived out of order.

  2. 02

    Identity is necessary—but Match membership is a separate check

    The frontend sends a user and Match identifier in the socket handshake. In this codebase, DEV_PRINCIPAL enables a development-only identity seam; it is not a production authentication implementation. The Game verifies that the principal can snapshot that Match before registering Presence and joining its room. Later action handlers take identity from the attached principal, not from a user ID in the command body.

    Do not confuse a claimed ID with authorization

    A socket test can show how the development handshake rejects missing/conflicting values. It does not prove production login, and a valid user identity alone does not grant access to every Match.

  3. 03

    Presence changes; gameplay status and the Match clock do not pause

    Presence is not Player status. A socket disconnect moves connectivity to offline; it does not replace a running or evaluating activity with a made-up “disconnected” gameplay state. A Run or Submission already in the Game continues, and the Match clock keeps moving.

    The Game counts sockets per user and Match: the first socket marks online; only the last close marks offline. In 1v1, Presence is per side and an expired reconnect grace can forfeit. In 2v2, Presence is per member, and an offline member's grace expiry does not forfeit the Match.

  4. 04

    Rejoin with a fresh baseline; do not mistake local draft for Match state

    On a browser network return, the transport opens a fresh socket and waits for the server snapshot. Game joins the authorized Match room before sending that baseline; subsequent event refreshes converge on current truth, and the client drops demonstrably stale revisions. The saved editor draft is local to the browser (see Lesson 5); the Match phase, clock, submissions and Reveal come from the server.

    Live Match events are notifications, not a replayable event log. Each event prompts the client to fetch the authoritative snapshot from /snapshot; after reconnect, the client obtains a fresh baseline. Missed individual events are not replayed. The client compares event and snapshot revisions with the newest applied revision, so an older committed revision cannot move its view backward. Snapshot recovery restores current Match state, not a history of every event.

    A source-level E2E scenario checks network drop, the opponent's continuing actions, clock movement, preserved draft, and resumed controls. Another covers a hard reload. Those scenarios are test code; do not call them a fresh browser-test pass for this lesson.

    The Postgres-backed reconnect suite was inspected but not run here: it boots a local Game listener and uses TEST_PG_URL. This restricted session has already refused local listener startup, so its service scenarios remain source evidence only.

    Scale-out limit in the current evidence

    The socket-count tracker is an in-process Map. These single-service tests do not establish correct Presence coordination across multiple Game instances or a distributed socket adapter.

A reconnect is not a service restart

Browser disconnect, Game process still running

Game state and the Match clock continue. The socket closes, Presence follows last-socket accounting, and the returning browser requests a current snapshot. The editor draft is a separate local concern.

Game service process restarts

Durability and boot repair become the question instead. Follow Lesson 8 for the Postgres/in-memory distinction and pending-Evaluation recovery.

The Game's Socket.IO room and this process-local Presence tracker are not proof of horizontal scale-out. The auth code shown here is explicitly a development seam.

Check the model in your head

What does reconnect restore, and what does it not change?

Try answering without reopening the trace. Hint: name one server value, one browser-local value, and the two distinct connection/gameplay states.

Show a useful answer

The client joins again and receives an authoritative server snapshot, so current Match phase, clock, Submissions and any Reveal can render. The editor draft is local browser state, not part of that Match snapshot. Presence follows socket counting; Player status remains the gameplay activity, and disconnect alone does not pause the Match clock or cancel a server Evaluation.

Rewrite-test prompt

Test these independently: a participant can rejoin their Match and gets a fresh server baseline; an unrelated authenticated user cannot join that room; stale revisions do not overwrite newer state; opening a second tab and closing the first keeps the user online; in 2v2 one member can go offline without marking their teammate offline; and Player status/Match time continue during a disconnect. Keep HTTP, socket handshake, membership authorization, and production authentication as separately testable boundaries.

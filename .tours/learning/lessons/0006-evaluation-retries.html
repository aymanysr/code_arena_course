A retry is the same Evaluation only when its identity matches

In about 9 minutes: Explain which IDs and submission fields make a retry idempotent, why changed data under an old ID is rejected, and what the focused tests do not prove about durable cross-process claims.

First, make a prediction

The network drops after Submit. If the client sends the same IDs again, should the judge run a second time?

A retry should not accidentally become a second attempt—but reusing an ID for changed code must not rewrite the first request.

Check your prediction

It is the same logical Evaluation only when the IDs and the immutable submission identity still match. A conflicting payload using an old Evaluation ID is rejected. A genuinely new Submit gets new IDs.

Now follow the identity

An Evaluation ID names work; the rest of the fields prove which work it means

  1. 01

    The engine binds an ID to a specific submission

    If callers omit them, the engine makes a submissionId and an evaluationId. It also computes a hash of the submitted source. To accept a reused evaluationId, it compares Match, Round, side, submission ID, problem version, language, source hash, and (for a shared team document) document revision.

    So “same Evaluation” means more than “same button was clicked.” Same ID + changed code is a conflict, not permission to change the accepted work.

  2. 02

    Concurrent retries attach to the accepted work

    The in-flight registry is explicitly process-local: while one request is evaluating, a matching retry can wait for that same completion. Durable claim acquisition is a separate persistence contract. The orchestrator claims before invoking the Judge and releases the claim after evaluation/commit; this is why “the local map exists” alone is not proof of cross-process safety.

  3. 03

    Same ID with different data is rejected—even after completion

    The tests try changing the code while keeping an in-flight ID, then try reusing a completed ID with a conflicting payload. Both are rejected; the in-flight example shows no second Judge execution. In contrast, a new Submit call creates fresh IDs.

  4. 04

    A Judge failure is not automatically a new contestant verdict

    When an in-flight Judge failure occurs, the duplicate waiting on that same request receives the same failure; the test verifies the Judge ran once. Another test shows an infrastructure failure does not replace an earlier counted score. These are specific tested paths—not a promise that every error is safely retryable or that every network retry is recognized.

Keep three guarantees separate

Request idempotency: a matching repeated request does not create duplicate work. Evaluation claim: persistence grants one worker ownership of pending work. Judge: executes the code and returns a verdict; it does not decide whether an ID is valid. Lesson 8 will trace what the durable store can recover after a process restart.

Check the model in your head

A request repeats evaluationId=E7, but its source has changed. Should it attach to the first Judge call?

Before opening the hint, name at least two identity fields besides the Evaluation ID.

Show a useful answer

No. The source hash no longer matches, so the engine rejects reuse of E7 with different submission data. A retry keeps the original IDs and the original payload. A deliberate new attempt gets new IDs and follows the new-submission rules.

Rewrite-test prompt

Write separate tests for: same IDs + same payload returns the same outcome and invokes the Judge once; same Evaluation ID + changed code is rejected before duplicate work; a new Submit receives fresh IDs; and a Judge infrastructure failure is not converted into a contestant score. Then test persistence claims across two Game instances using the real database before claiming cross-process protection.

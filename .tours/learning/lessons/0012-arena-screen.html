Code Arena Learning Map / Lesson 12

The Arena screen is a view of Match state—not another game engine

In about 9 minutes: Trace how the app chooses a mock or live transport, how an Arena snapshot becomes visible screen sections, and where display responsibilities stop.

Source references match 18 pinned files Snapshot 818ea4603e970d66

1 · Predict → 2 · Trace → 3 · Recall

First, make a prediction

A new snapshot says “SCORE_REVEAL.” Which part of the screen changes—and who decided the score?

Choose before tracing: the phase banner, the Arena page, the UI component that draws the reveal, or the game engine.

Check your prediction

The Game owns phase changes and scoring. The transport gives React a current ArenaSnapshot; ArenaPage reads its phase and conditionally shows the workspace and Reveal. PhaseBanner prints the phase in words, while RoundScoreReveal displays the already-built Reveal. Those components present game state; they are not the scoring authority.

Key terms

ArenaSnapshot
A current view of the Match and Round, including phase, clock, problem, player/team display data, visible tests, and any published Reveal.
ArenaPage
The React composition point that subscribes to the transport snapshot and chooses which screen pieces to show for that state.
Display component
A small component that turns supplied props into visible text or controls. Showing a score or phase does not mean that component calculated or authorized it.
Mock transport
An in-memory teaching/demo adapter. It can drive the same screen, but it is not the live Game service.

Now follow one snapshot

The data flows into the screen; the screen does not invent Match truth

  1. 01

    The app chooses a live or mock transport

    main.tsx mounts React's App. In the default demo route, App creates a MockArenaTransport. With ?live=1 and a Match ID, it connects a SocketArenaTransport; if the live flag has no Match ID yet, it shows the Lobby instead. Keep this distinction in mind: a convincing mock screen is not a production-server test.

  2. 02

    ArenaPage subscribes, then keeps the phase visible

    ArenaPage calls useArena(transport) to read the current snapshot. It always renders the header and phase banner from that snapshot. The header shows mode, remaining time, and transport connection; the banner turns roundPhase into a short human-readable message. Neither component changes the Match phase.

  3. 03

    The phase decides which screen sections appear

    During MATCH_FOUND or ROUND_INTRO, the page offers Start round. During CODING or SCORE_REVEAL, it loads the workspace. For an expired Match, MATCH_COMPLETE first shows the saved Round Reveal, followed by a See final result button. That button changes only the presentation; the current snapshot computes the final result from saved Match state. In an ordinary completion with time remaining, the page can render the Match result immediately. That is UI branching on supplied values—not a second game state machine.

  4. 04

    The workspace arranges panels; MatchPanel chooses duel or teams

    ArenaWorkspace places the Problem, Code workspace, and Match panel into one responsive grid. Inside that panel, MatchPanel selects DuelPanel for 1v1 or TeamPanel for 2v2. Those smaller components format supplied player/team values. Team Ready is an action callback, not authority: the page routes it to the transport, while Lesson 10 traces the Game's readiness rules. Status text comes from an explicit label map rather than color alone.

    TestPanel similarly displays visible-test state passed in the snapshot. Its “Passed” label is not the Judge: Lesson 5 follows the action that actually runs those examples.

Hint, then check yourself

Trace: transport provides snapshot → ArenaPage reads phase → PhaseBanner labels it → page includes the workspace and Reveal view when their conditions match. The Game already owns the phase and score; the components present them.

Rewrite-test prompt

For a rewrite, feed a known Match snapshot into your screen and assert the phase label, Round number, correct 1v1/2v2 panel, visible-test text, and Reveal/result appear only in their corresponding phases. Separately test that an action button sends a command and let a Game-rule test decide whether that command is accepted. Do not make the UI calculate a scored Reveal or mistake the mock adapter for live behavior.

How this lesson helps your build: Connect players to the rules

Why this comes now: The screen should send commands and show the Match state owned by the server.

What must exist first: Save accepted Match state

Where it belongs: In a similar layout, find the game service under services/game/src/game/, transport under frontend/src/arena/transport.ts, and screen under frontend/src/components/. Test each at its boundary.

Pattern: The screen sends commands and shows server state. Transport handles delivery and reconnect.

What to create: Add a service route, transport, basic Arena screen, and reconnect snapshot behavior.

How to check it: Two browser clients see the same saved Match. After reconnect, the client loads its current state.

What to build, and why this order

Read the steps from top to bottom. Each step uses something made earlier. The paths are examples from this repo; find the matching owner in your teammate's repo before creating files.

  1. Find the homes

    Why now: First find where this repo keeps rules and tests. That way you add files beside the code that owns them.

    Needs: No earlier build step

    Create: Write down the game package, test folder, frontend app, service route, storage module, and run commands.

    Place: Use the paths that already exist in your teammate's repo. If it looks like this repo, inspect packages/, services/, and frontend/ first.

    Pattern: Keep each rule, route, test, and data file near its current owner.

    Check: You can name the test command and folder where a Match rule test should go.

    Read: Lesson 13

  2. Make a small Match core

    Why now: Submit needs a Match, an active Round, a player, a phase, and a clock.

    Needs: Find the homes

    Create: Create Match and Round state, legal phase changes, score rules, a fixed clock, and a fake Judge test helper.

    Place: Use the existing game-rules package. In a similar layout, create packages/arena-game/src/match-rules.ts and packages/arena-game/test/match-rules.test.ts.

    Pattern: Keep phase and score choices in a pure rule module. Pass in the clock and fake Judge result in tests.

    Check: A fixed-clock test starts a Match and Round, then rejects an action in the wrong phase.

    Read: Lesson 3

  3. Give a player a Problem and Run

    Why now: A player and visible Problem must exist before code can be checked or submitted.

    Needs: Make a small Match core

    Create: Add basic Match entry, one checked Problem, and a Run that returns example feedback without changing the score.

    Place: In a similar layout, put Match entry near packages/arena-game/src/lobby.ts and its test near packages/arena-game/test/lobby.test.ts. Put Problem data under packages/problem-bank/problems/.

    Pattern: Keep Problem data separate from Match rules. Run returns visible feedback and does not change the score.

    Check: An admitted player can Run visible examples. A visitor is rejected, and no Run changes the score.

    Read: Lesson 4 · Lesson 5

  4. Add Submission and Reveal

    Why now: Now the game can decide when code may enter hidden tests and when its score can be shown.

    Needs: Give a player a Problem and Run

    Create: Add Submit, a pending receipt, retry identity, a fake-Judge result, the deadline cutoff, score update, and Reveal.

    Place: In a similar layout, extend packages/arena-game/src/engine.ts and add a test in packages/arena-game/test/submit-path.test.ts. Use the Judge interface your repo already has.

    Pattern: Game rules decide if Submit is legal, storage records acceptance, and the Judge runs code. Use the same request ID for a retry.

    Check: A valid Submit is judged once. Submit after Round close is rejected. Hidden results appear only at Reveal.

    Read: Lesson 1 · Lesson 2 · Lesson 6 · Lesson 7

  5. Save accepted Match state

    Why now: Reconnect and restart need to recover saved Submissions and Reveals.

    Needs: Add Submission and Reveal

    Create: Add one Match storage contract, an in-memory version, then a database adapter and restart tests.

    Place: In a similar layout, extend packages/arena-game/src/persistence.ts and packages/arena-game/test/persistence.test.ts, then use the existing database adapter.

    Pattern: Test one storage contract with memory and the real database. Reject writes based on an old revision.

    Check: After restart, the same accepted Submission and Reveal are loaded. An old write cannot replace newer state.

    Read: Lesson 8

  6. Connect players to the rules

    Why now: The screen should send commands and show the Match state owned by the server.

    Needs: Save accepted Match state

    Create: Add a service route, transport, basic Arena screen, and reconnect snapshot behavior.

    Place: In a similar layout, find the game service under services/game/src/game/, transport under frontend/src/arena/transport.ts, and screen under frontend/src/components/. Test each at its boundary.

    Pattern: The screen sends commands and shows server state. Transport handles delivery and reconnect.

    Check: Two browser clients see the same saved Match. After reconnect, the client loads its current state.

    Read: Lesson 9 · Lesson 12

  7. Add two-player teams

    Why now: Shared editing and Ready checks need Match rules, storage, and live messages first.

    Needs: Connect players to the rules

    Create: Add 2v2 teams, a shared revision, Readiness reset after edits, team-only chat, and reconnect tests.

    Place: In a similar layout, extend packages/arena-game/src/team-collaboration.ts and its test. Keep clients in frontend/src/arena/collab.ts and chat.ts.

    Pattern: Game rules own Readiness and revision. Collaboration and chat clients deliver team-scoped updates.

    Check: Four users stay separated by team. An edit clears both Readiness approvals.

    Read: Lesson 10 · Lesson 11

  8. Check the real boundaries

    Why now: Fake tests do not prove PostgreSQL, Docker isolation, or real browser behavior.

    Needs: Add two-player teams

    Create: Run equivalent database, Judge security, and two-client browser checks in your teammate's repo. Record checks that could not run separately.

    Place: Use the existing database, Judge, and browser test folders. In a similar layout, inspect packages/arena-game/test/judge-security.test.ts and frontend/e2e/.

    Pattern: Keep fake, database, Docker, and real-browser evidence separate. Record the command and result for each.

    Check: Mark PASS only after the matching test runs in your teammate's repo and passes.

    Read: Lesson 14

Ownership map

When a change crosses one of these boundaries, the owning module should remain the place where the rule is decided.

Frontend

frontend/src/arena + components

Turns authoritative snapshots into UI and sends user intent through transport seams.

Owns
  • editor interaction
  • snapshot rendering
  • connection UX
  • client sidecars
Does not own
  • score calculation
  • hidden tests or opponent source

Game service

services/game/src/game

Composes HTTP, sockets, principals, persistence selection, and event fan-out around the domain package.

Owns
  • request boundary
  • socket namespaces
  • service lifecycle
  • presence gateway
Does not own
  • round scoring rules
  • judge provider details

packages/arena-game/src

Defines the match model and keeps all competitive decisions behind server-side domain seams.

04 · Why the seams exist

Architecture guardrails

These cards are the short version of the ADRs. They explain the boundary decisions without asking teammates to open twelve documents first.

ADR-0005 · transport seam

One client-facing transport interface

Live sockets, mocks, and future transports can vary without spreading connection mechanics through UI components.

ADR-0003 + ADR-0012 · judging

Untrusted code crosses one GameJudge boundary

ContainerJudge is the default isolated runner. Judge0 is an optional adapter, not a second game authority or a fallback that silently changes behavior.

ADR-0004 · persistence

Match persistence is a deep module

ArenaEngine depends on MatchPersistence; Postgres and in-memory stores can change without changing the MatchRecord contract.

ADR-0011 · concurrency

Claims and revisions protect recovery

Evaluation claims prevent duplicate work across processes; expected revisions reject stale ordinary writes instead of replaying them.

ADR-0006 + ADR-0009 · sockets

Authorization and presence stay server-side

Socket context is resolved from the trusted principal, while first/last socket presence policy stays in the Game service.

ADR-0008 · collaboration + chat

Realtime sidecars have explicit lifecycles

Team collaboration is round-scoped; team chat is match-scoped; neither bypasses the authoritative game state.

ADR-0001 + ADR-0002 · ownership

Game owns first-release match chat

The service boundary leaves room for a future Chat service, but the current game-owned chat is the intentional delivery path.

Hybrid role model, explained in one puzzle

One concrete 90-second scenario, shown twice. A team gets a tiny buggy function and 90 seconds to fix it, prove it with a test, and submit. Nothing here is built, approved, or playable — this page only sketches how work could be split so nobody sits idle.

The example used everywhere below.
Puzzle: sum_even(numbers) should return the sum of the even numbers.
Starter code (buggy): total = 0; for n in numbers: total += n; return total — it sums everything.
The fix is one condition: only add n when n % 2 == 0. The interesting part is who writes what, who runs what, and who sees what.

1 · Two-player flow

Two roles, one shared 90 seconds. The main editor has a single owner at a time, but the test console never locks — the second player is always doing real work, not watching.

Solution Driver (owns the main editor)

  • TypesThe candidate fix in the main editor, e.g. adding if n % 2 == 0: around the addition.
  • ClicksLock edit when ready for a check; Pass editor to hand control over voluntarily; Submit at the end.
  • Sees privatelyThe editable solution pane plus the shared test results. Cannot silently edit anyone else's test or watch entries.
  • ContributesThe only version of the solution the team can submit. Every revision flows through this editor.

Test & Debug Partner (independent console)

  • TypesA test input and assertion, e.g. input [1, 2, 3, 4], expects 6; plus a breakpoint like line 3: total and a watch like n.
  • ClicksRun test any time, without asking; Add watch to track a variable; Accept editor if the Driver passes control.
  • Sees privatelyTheir own test console and watch values (e.g. “run 2 failed: got 10, wanted 6”). The Driver sees the same result row, but only the Partner authors the test.
  • ContributesThe proof the fix works — adversarial inputs, expected outputs, and the runtime inspection that explains why it failed.

Passing, not taking. Either player can offer the main editor, and the other accepts. Nobody can grab it. In the demo below, try Pass editor control and watch the owner pill change.

2 · Three-player flow

Same puzzle, finer split. Three roles so testing and debugging each get a dedicated owner — but again, only the main editor is single-owner.

Solution Driver

  • TypesThe candidate solution, same as above.
  • ClicksLock edit, Pass editor, Submit.
  • Sees privatelyEditable solution + shared results feed.
  • ContributesThe submittable fix.

Test Engineer

  • TypesAdversarial cases: [] → 0, [1,3,5] → 0, [2,4] → 6, and the assertion text.
  • ClicksRun test independently and repeatedly.
  • Sees privatelyTheir test authoring pane and per-case pass/fail rows.
  • ContributesCoverage that catches “sums everything” versus “sums evens”.

Debug Engineer

  • TypesBreakpoints (pause each loop pass), watches (n, total), and a one-line reading (“total grew on odd n=3, so the filter is missing”).
  • ClicksAdd watch, steps through paused state (simulated here).
  • Sees privatelyWatch values per loop pass and the breakpoint hit list.
  • ContributesThe explanation that turns a red test into the correct one-line fix.

3 · One shared loop (both team sizes)

Two players or three, the loop is identical. Concrete pass through the example:

  1. 1
    Write solution.
    Driver drafts the even-only fix.
  2. 2
    Construct test.
    Partner / Test Engineer adds [1,2,3,4] → 6.
  3. 3
    Run.
    Anyone runs; result row appears for all (simulated).
  4. 4
    Inspect state.
    Debug side reads watches: odd values leaked into total.
  5. 5
    Revise or pass.
    Driver revises — or passes the editor to whoever sees the fix.
  6. 6
    Submit.
    Team submits the locked solution + test report.

4 · The one ownership rule

Single-owner editor, always-on side consoles

Only the main solution editor has one owner at a time. The test console and the debug console stay independently active for their owners at all times. That is the whole anti-idleness trick:

  • While the Driver types the fix, the Partner is already writing the failing test.
  • While a test runs, the Debug Engineer is already placing the next watch.
  • Passing the editor never freezes anyone — tests and watches keep working before, during, and after the handoff.

5 · How this differs from the obvious alternatives

ModelWho does whatFailure mode this sketch avoids
Hybrid (this sketch) One editor owner + independent test / debug consoles; voluntary pass. Nobody waits: every role types, runs, and explains on every loop.
One coder + passive helpers One person edits; others watch or shout suggestions. Helpers go passive — no console of their own, nothing to run or inspect.
Simultaneous shared editing Everyone types in the same file at once. Cursor collisions and “who broke it?” — tests and inspection get crowded out by edit churn.

7 · Three review prompts

  1. Does every role feel active? Is there any point in the 90 seconds where a role has nothing to type, run, or explain?
  2. Would you enjoy each role? Driver, tester, debugger — which would you pick first, and which would you dread?
  3. Should editor ownership rotate automatically or only when passed? Timer-based rotation, or strictly voluntary handoff?
